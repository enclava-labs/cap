Enclava Deploy Flow: No Env Exports

The CLI discovers deployment context from the authenticated CAP API, builds a signed descriptor locally, and lets the platform create a tenant runtime from pinned GHCR image digests.

Product shape implemented
User and CLI Simple deploy command. No platform internals exported into the shell.
1

Run deploy

enclava deploy --image ghcr.io/...

2

Discover context

CLI calls /platform/deployment-context with the logged-in session.

3

Receive platform facts

API returns the signing public key and TLS certificate broker URL.

4

Build signed descriptor

The CLI signs a deploy descriptor that binds image digest, policy, and context.

CAP control plane Authenticated API validates intent and turns it into tenant resources.
5

Validate descriptor

CAP API checks the signed request against platform policy and deploy inputs.

6

Create tenant namespace

Kubernetes namespace is created for the app, for example cap-org-app.

7

Pull GHCR digests

Runtime containers use pinned GHCR digests instead of mutable local images.

8

Expose app URL

The platform publishes the tenant HTTPS endpoint for the deployed app.

Claim, unlock, runtime TEE evidence and storage unlock gate the app before it serves traffic.
9

Claim or unlock

The user verifies TEE evidence and unlocks encrypted tenant storage.

10

Start runtime

enclava-init prepares the pod, then app containers become ready.

11

Serve HTTPS

tenant-ingress routes public HTTPS traffic to the web app.

12

Keep attestation available

attestation-proxy remains available for runtime attestation flows.

What changed for users

Before Manual config exports
  • ENCLAVA_API_SIGNING_PUBKEY had to be known by the user.
  • TLS_CERTIFICATE_BROKER_URL had to be set in the shell.
  • Deploy UX exposed internal platform wiring.
Now Authenticated context delivery
  • The API returns the current runtime signing key.
  • The API returns the correct TLS broker URL for the environment.
  • The CLI can deploy without extra env-var ceremony.

Runtime shape

  • web is the customer app image.
  • tenant-ingress terminates and routes tenant HTTP traffic.
  • enclava-init prepares confidential runtime state before app readiness.
  • attestation-proxy serves attestation-related runtime APIs.
web Customer workload image from GHCR digest.
tenant-ingress Public HTTPS entry point into the tenant pod.
enclava-init Init and unlock-sensitive runtime setup.
attestation-proxy TEE evidence and attestation service path.
Security boundary: platform facts come from the authenticated CAP API, not user-managed shell exports. Release boundary: cluster workloads pull committed GHCR image digests.
