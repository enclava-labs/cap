Enclava Flow: Signup to Running Confidential App

A user creates an account, prepares an app, deploys a pinned GHCR image, and unlocks a confidential runtime. Platform signing and TLS broker context are discovered by the CLI from the authenticated API.

No env exports during deploy

1. Register

Email or Nostr signup creates the user, session, and personal org.

2. Prepare

The CLI writes app config, workflow scaffolding, and app identity.

3. Deploy

The CLI signs the deploy descriptor and CAP turns it into Kubernetes state.

4. Unlock

TEE attestation and storage unlock gate the app before it serves HTTPS.

User Email or Nostr identity enclava signup creates the account.
Session CLI credentials Session token is saved locally for API calls.
Org Active organization Signup creates a personal org; users can create or switch orgs.
App App record enclava create registers app settings and identity anchors.
Tenant Kubernetes namespace CAP creates isolated runtime resources for the app.
Runtime HTTPS endpoint The app becomes reachable after claim or unlock completes.
A

Account

User registration and active org selection.

1

Sign up

enclava signup prompts for Email or Nostr. The API creates the user and returns a session token plus default org.

2

Log in later

enclava login refreshes local credentials and sets the active organization for future commands.

3

Use an organization

Optional team setup uses enclava org create, enclava org switch, and org invites.

B

Project

Local app shape becomes platform app identity.

4

Initialize app config

enclava init detects the Dockerfile port, writes enclava.toml, and creates a GitHub Actions workflow.

5

Create platform app

enclava create reads enclava.toml, creates the app, and saves the bootstrap owner key in password mode.

6

Build signed image

GitHub Actions or a local build publishes an image to GHCR and deploys by immutable @sha256 digest.

C

Deploy

API-delivered context replaces user-managed exports.

7

Run deploy

enclava deploy --image ghcr.io/...@sha256:... starts the signed deployment flow.

8

Discover platform context

The CLI calls /platform/deployment-context and receives the API signing public key plus TLS broker URL.

9

Submit signed descriptor

CAP validates the descriptor, policy artifacts, image digest, and app inputs before applying Kubernetes manifests.

D

Runtime

Confidential pod starts only after attested ownership flow.

10

Pull pinned images

Kubernetes starts tenant containers from committed GHCR digests: app, ingress, init, and attestation proxy.

11

Claim or unlock storage

The CLI attests the TEE, signs the bootstrap challenge, and prompts for the initial storage password or unlock password.

12

Serve the app

tenant-ingress exposes public HTTPS while attestation-proxy remains available for runtime proofs.

Runtime containers

web Customer workload image pulled by immutable GHCR digest.
tenant-ingress Public HTTPS entry point into the tenant runtime.
enclava-init Init and unlock-sensitive setup before app readiness.
attestation-proxy TEE evidence and attestation service path.

Config and release contracts

Context CAP API returns platform signing and broker facts.
Descriptor CLI signs the deployment descriptor with app and image inputs.
Attestation TEE evidence is checked before claim, unlock, or config delivery.
Release Cluster workloads run committed GHCR images by digest.
User-facing path: signup, login, init, create, deploy, claim or unlock. Security boundary: platform facts come from authenticated CAP API context discovery.
